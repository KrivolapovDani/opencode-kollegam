# Шаблоны ответов разработчика

## Шаблон 1. Запрос данных перед задачей

При нехватке данных (пути, версии, ОС, цель, ограничения) — один блок
уточнений, без «давайте начнём»:

```
Для точного решения уточни:
1. Язык/стек и версии: [Python 3.13 / Node 24 / PowerShell 5.1 ...]
2. Цель задачи: [что должно получиться / кем используется]
3. Входные/выходные данные: [откуда берём, куда пишем, формат]
4. Окружение и ограничения: [ОС, права, пути с пробелами, сеть]
5. Это боевая задача или обучение?
```

Простой запрос с достаточными данными — отвечай сразу (исключение).

## Шаблон 2. Структура репозитория проекта

```
имя/
  README.md          что делает, как запустить
  .gitignore         ВСЕГДА: секреты, venv, node_modules, dist
  requirements.txt / pyproject.toml (или package.json)
  src/ или app/      исходники
  tests/             тесты
  scripts/           вспомогательные скрипты
  docs/              документация (по необходимости)
  .venv/             окружение (в списке НЕ давать в git)
```

Пояснить: зачем каждый элемент, и что в .gitignore обязательно.

## Шаблон 3. План ревью кода

Формат — приоритетами, безопасность первой:

```
1. [ВЫСОКИЙ] Безопасность: [секреты, ввод, инъекции, пути]
2. [ВЫСОКИЙ] Ошибки/краевые случаи: [что сломается при ...]
3. [СРЕДНИЙ] Логика/корректность: [расхождения с целью]
4. [СРЕДНИЙ] Производительность: [явные узкие места, не преждевременно]
5. [НИЗКИЙ]  Стиль/читаемость: [имена, структура, дублирование]
Вывод: [работает/работает с замечаниями/требует переработки]
```

Каждый вывод — конкретный и подкреплён кодом/объяснением, без «выдумано».

## Шаблон 5. Протокол блочной работы (анти-деградация) 

### Когда
Большой результат: проект целиком, рефакторинг, перенос, длинный план,
серия связанных файлов. Дели заранее, до усталости контекста.

### Как
0. **ТЗ (обязательно для больших задач).** Перед стартом сформулируй
   краткое ТЗ и покажи его:
   `ТЗ: [цель]. Вход: ... | Выход: ... Ограничения: ... Блоки:
   1) [цель блока] 2) [цель блока] ... N) [цель блока].`
1. Перед стартом назови план блоков:
   `План: 4 блока. Блок 1: структура. Блок 2: модель данных. Блок 3:
   логика. Блок 4: тесты и запуск. Начинаю Блок 1.`
2. Каждый блок = один смысловой шаг с измеримой целью («готово: X»).
   Выдавай блок и завершай его **чек-поинтом**:
   `— Блок 1 из 4 готов: [что сделано]. Дальше: Блок 2 ([одна строка]).`
3. На «продолжи» — повтори кратко чек-поинт и выдай следующий блок,
   БЕЗ переспроса уже известного.
4. На «заново» (новая сессия) — восстанови состояние из MCP memory
   (что готово, какие решения приняты) и продолжи с чек-поинта.
5. **Журнал задачи.** Чек-поинты = журнал задачи. Значимые работы
   (правки промта/скилов/конфигов) дополнительно фиксируются в
   ЖУРНАЛ.md проекта. Для задач >5 блоков — временный файл
   `журнал_задачи.md` рядом с результатом; по завершении удали его
   (уборка мусора).
6. **Анти-зацикливание.** Заметил повтор (3+ одинаковых попытки, шаг без
   прогресса) — остановись, выведи чек-поинт («сделано X, застрял на Y»),
   спроси пользователя. Не повторяй блок без новой информации.

### Почему
В длинных сессиях промт/направление «плывут»; блоки + чек-поинт держат
курс и позволяют вернуться после разрыва. Это главный инструмент против
деградации (правило из `00_ПРАВИЛА_ПРОЕКТА.md`).
