# Самоанализ, тесты и рост агента-разработчика

Запускается ТОЛЬКО по явному запросу: «тест разработчика», «прогон»,
«самоанализ», «доработай промт», «улучши промт», «рефлексия», «meta»,
«регрессия», «обнови». В обычных ответах этот скил не подгружается.

## 1. Бенчмаркинг по критериям

Оцени текущий уровень агента по шкале 1–10 (честно):

1. Инструменты/версии — точность названий (dev-registry).
2. Безопасность и секреты — запреты соблюдены (dev-guardrails).
3. Шаблоны и блочная работа — используются при длинных задачах.
4. Сравнительный анализ и база формул — применяются при выборе.
5. Проверки перед сдачей — 41 протокол (dev-checks).
6. Корректность кода — синтаксис и запускаемость.
7. Обучение — объяснения новичку на уровне ученика.
8. Память — лучшие формулы сохраняются/восстанавливаются (MCP memory).
9. Противостояние деградации — ТЗ→блоки→цели→журнал, чек-поинты,
   восстановление после «заново», анти-зацикливание.
10. Формат и тон — под задачу, без воды, точные команды.
11. Журнал ошибок — замеченные ошибки фиксируются, самоанализ проверяет.
12. Уборка мусора — после задач временные файлы/артефакты удалены.

## 2. Метрики

- Средний балл по критериям (сумма/10).
- Какие критерии ≥8 (сильные), какие <6 (проседают).
- Честная фиксация: «что тестировалось реально» ≠ декларация.

## 3. Шаблон «САМОАНАЛИЗ»

```
САМОАНАЛИЗ (dev-reflexion, vX.Y)
Датa/хэши: [дата; хэш промта/скилов SHA-256]
Средний балл: X.X /10
Сильно: n1, n2.
Слабо: n3 (причина), n4 (причина).
Причина слабости: [в промте / в скиле / в исполнении / в контексте].
Решение: [править X | не править — слабость в исполнении].
```

## 4. Протокол прогона тестов (команда «тест разработчика» / «прогон»)

Выполняется в СВЕЖЕЙ сессии (чистый контекст) — это строгий замер.
Одна сессия = один прогон. Шаги:

1. Найди файл плана тестирования: `01_план\план_тестирования.md`
   (в подпроекте `02_разработчик`; если путь другой — поиск по имени).
2. Прочитай контрольные запросы (6 шт.) и чек-лист (12 пунктов).
3. Зафиксируй хэши промта и скилов (SHA-256) — сверь с отчётом.
4. Выполни 6 запросов ПОДРЯД: для каждого сформулируй ответ по протоколу
   промта (5 шагов мышления, скилы по вызову, чек-лист в конце).
   Вопросы можно варьировать по форме, но НЕ по смыслу.
5. Оцени каждый ответ по чек-листу: 1 балл за пункт, макс. 12.
6. Порог приёмки: **все запросы ≥ 11/12**. Провал → найди причину
   (промт/скил/MCP/исполнение), исправь, перепрогони только этот сценарий,
   затем общую регрессию.
7. Запиши результат в `01_план\ОТЧЁТ_ТЕСТ.md` (таблица «запрос → балл →
   замечания»), обнови хэши и дату.
8. Выдай пользователю сводку: баллы по 6 запросам, порог, вывод.

## 5. Правило регрессии (19) — обязательно

**Любая правка промта/скила/конфига → прогнать контрольные запросы
(6 шт. из 01_план\план_тестирования.md), порог ≥11/12. Провал → откат
по снапшоту или исправление причины и повтор.**

Плановая регрессия (правило 20): раз в 2–4 недели, даже без правок.

## 6. Протокол роста скилов (автообновление)

1. Агент находит повторяющийся паттерн: новая удачная технология /
   повторная ошибка / найденный инструмент.
2. Предлагает: обновить существующий скил ИЛИ создать новый (по форме
   SKILL.md: frontmatter name+description → структура).
3. Пользователь подтверждает (ОБЯЗАТЕЛЬНО).
4. Снапшот текущей версии (копия в историю/журнал).
5. Правка/создание SKILL.md.
6. Регрессия (правило 19) — порог ≥11/12.
7. Запись в журнал авторегенерации (см. ниже).
8. Синхронизация канон(`03_скилы`) ↔ рабочая
   (`%USERPROFILE%\.config\opencode\skills`) — сверка SHA-256.

**Запреты:** никогда не удалять скилы; dev-guardrails — только с явного OK
пользователя, независимо от степени автономии.

## 7. Журнал авторегенерации

Каждая регенерация/рост фиксируется в `02_разработчик\ЖУРНАЛ.md`:
- что изменено, почему, когда;
- снапшот (куда сохранён);
- результат регрессии (баллы по 6 запросам);
- частая ошибка: «скил сам себя улучшил и сломал» — она же причина
  обязательности регрессии.

## 8. Триггеры

- По команде пользователя: «тест разработчика», «прогон», «самоанализ»,
  «доработай промт», «улучши промт», «рефлексия», «meta», «регрессия», «обнови».
- После серии из 5+ сложных запросов — предложи провести самоанализ.
- При прощании — напомни: рост/регрессия по правилам 19–20.
- В любом случае: без явного запроса — скил НЕ загружать.

## 9. Журнал ошибок, анти-зацикливание и уборка мусора

### Журнал ошибок (ЖУРНАЛ_ОШИБОК.md)
- Файл: `02_разработчик\ЖУРНАЛ_ОШИБОК.md`.
- Фиксация: заметил свою ошибку по ходу работы (повтор, неверная команда,
  потеря контекста, зацикливание, мусор) — запиши сразу: ошибка, где,
  причина (промт/скил/исполнение/контекст), статус (открыта/устранена).
- Проверка: при «самоанализ» / «тест разработчика» / «прогон» — прочитай
  журнал, проверь статусы, предложи устранение (правка промта/скила),
  закрой устранённые, зафиксируй результат в ЖУРНАЛ.md.
- Автономность: журнал лежит в подпроекте — работает при передаче
  только разработчика (у учителя — свой журнал).

### Общая база ошибок коллег (oshibki-kollegam)
- Путь: `%USERPROFILE%\Documents\oshibki-kollegam\` (у каждого коллеги свой,
  репозиторий общий). Если папки нет — подскажи пользователю запустить
  `install.ps1` из комплекта opencode-kollegam.
- При «самоанализ» / «тест разработчика» / «прогон»:
  1. `git pull` в папке базы — забрать чужие ошибки.
  2. Прочитай личный журнал (ЖУРНАЛ_ОШИБОК.md): устранённые ошибки →
     создай файл в базе по шаблону `_ШАБЛОН_ошибки.md`
     (имя: `ГГГГ-ММ-ДД_краткое-название.md`), заполни все разделы
     (Дата, Автор, Где, Симптом, Причина, Решение, Как предотвратить).
  3. Удали перенесённую запись из личного журнала (в журнале — только
     открытые ошибки).
  4. Если были изменения — `git add` + `git commit` + `git push`.
- Обновления комплекта: при запуске проверь, клонирован ли
  `opencode-kollegam` (папка рядом с базой); если да — `git pull`
  и сообщи пользователю о новой версии промта/скилов.

### Анти-зацикливание
- Детекция: 3+ одинаковых попытки / шаг без прогресса / повтор уже
  сказанного.
- Действие: остановись, выведи чек-поинт («сделано X, застрял на Y»),
  спроси пользователя. Не повторяй блок без новой информации.

### Уборка мусора
- После завершения задачи проверь и удали временные файлы, черновики,
  журналы задач, тестовые артефакты — если они не нужны пользователю.
- Включено в dev-checks (проверка G6).
